# Building the MOD PoC with Claude Code

Step-by-step guide for people. Claude Code does not need to read this file.

**How every "implement with Claude Code" step works**

1. Run the shell command: it opens Claude Code in the module folder, in plan mode.
2. Paste the prompt block into Claude Code, review the plan, approve it.
3. After it finishes: exit Claude Code (or use a second terminal), run the build-and-commit line, then `/clear` before the next step.

Paths in the prompts are relative to the module folder (`../contracts/…`).

---

## 1. Manual — set up the repository

```
unzip mod-poc-claude-md.zip && cd mod-poc
cp /path/to/MOD_Cloud_Platform_Architecture_Proposal.pdf docs/
git init && git status --short   # check that no secret files are listed
git add -A && git commit -m "specs and contracts"
```

## 2. Manual — set up access to Azure

No keys or secrets are needed to build or deploy the PoC: every Azure call uses your own `az login` session, and the deployed services use managed identities. Secrets the platform needs (JWT keys, passwords, SAS keys, the PoC CA) are generated by `up.sh` directly into Key Vault.

**What you need**

- An Azure subscription where you are **Owner**, or **Contributor + User Access Administrator** (the scripts create role assignments).
- Azure CLI 2.60 or later with Bicep, `jq`, and bash (Linux, macOS, WSL or Azure Cloud Shell).

**Sign in and select the subscription**

```
az login
az account list --output table
az account set --subscription "<subscription name or id>"
az account show --query "{name:name, id:id, user:user.name}" --output table
az bicep install && az bicep upgrade
```

**Check your permissions** (look for Owner, or Contributor and User Access Administrator):

```
az role assignment list --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --scope "/subscriptions/$(az account show --query id -o tsv)" --query "[].roleDefinitionName" -o tsv
```

**Keep secrets out of git**

- The repository ships a `.gitignore` that excludes `.env*` files (except `*.example`), `*.pfx`, `*.pem`, `*.key`, `secrets/` and `infra/.state/`. Do not remove these patterns.
- Never paste a secret into a prompt that asks Claude Code to write it into a file. If a value is needed locally, generate it with `infra/scripts/local-env.sh` (see `SETUP.md`).
- Before every commit, run `git status` and check that no `.env*.local`, certificate or key file is staged.
- To read a deployed secret, use `az keyvault secret show … --query value -o tsv` in your own terminal; do not store the output in a tracked file.

## 19. Manual — first deploy and data-path check

Replace `<portal-url>` and `<vault>` with the values printed by `up.sh`.

```
infra/scripts/up.sh --prefix modpoc      # grants you developer access by default (--developer)
PW=$(az keyvault secret show --vault-name <vault> --name admin-password --query value -o tsv)
TOKEN=$(curl -s -X POST https://<portal-url>/api/auth/login -H 'Content-Type: application/json' \
  -d "{\"userName\":\"admin\",\"password\":\"$PW\"}" | jq -r .accessToken)
curl -s -X POST https://<portal-url>/api/sim/power -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"targets":{"all":true},"on":true}'
sleep 180
curl -s https://<portal-url>/api/admin/collectors -H "Authorization: Bearer $TOKEN" | jq '.items[] | {name, status, lastSeenAt, freshnessAgeSeconds}'
```

Pass: all 8 collectors show `Enrolled`, a recent `lastSeenAt` and a freshness age under 60 s.

## Running modules locally

After the first deploy you can run the processing worker, the portal and the customer app on your machine against the deployed environment. Follow `SETUP.md`, section "Run a module locally"; it uses `infra/scripts/local-env.sh` to write git-ignored `.env*.local` files.

## If Claude reports a contract problem

Stop that step. At the repository root run `claude`, fix the file in `contracts/`, and commit it. Then repeat the affected steps for every module that uses that contract (see the contract index in the root `CLAUDE.md`).
