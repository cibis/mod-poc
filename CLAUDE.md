# Manufacturing Operational Data (MOD) Cloud Platform PoC — Repository Instructions

Loaded in every Claude Code session. PoC of the architecture in `docs/` (background only, do not read). Not product code. Human-oriented notes are in `BUILD.md`, `SETUP.md` and `docs/README.md`; you do not need them.

## Layout

```
/CLAUDE.md          this file
/BUILD.md           step-by-step build guide for people (do not read)
/SETUP.md           compile-and-run guide for developers (do not read)
/.gitignore         excludes secrets and local environment files
/contracts/         shared contracts
/conventions/       shared conventions (angular.md)
/infra/             Bicep + scripts
/edge/              simulated edge collector (controller space)
/platform/          database, ingest-api, management-api, processing
/portal/            admin portal + simulator (demo scaffolding): API + Angular
/customer/          customer reporting: API + Angular
/docs/              background for people
```

**Component names used in contracts:** `collector` = `edge`; `ingest-api`, `management-api`, `processing`, `db-migrator` = deployables of `platform`; `portal-api` / `admin-portal` = API / Angular app of `portal`; `reporting-api` / `customer-portal` = API / Angular app of `customer`.

## Working rules

- **Work task by task.** Each module `CLAUDE.md` has a task table naming, per task, the spec files in the module and the shared files to read. Read only those. One task per session; `/clear` between tasks.
- **Stay inside the module.** Do not open, read, search or modify other modules. The only exception is reading the files in `/contracts/` and `/conventions/` that your task row lists.
- **Contracts are fixed.** Implement them exactly. If one looks wrong, incomplete or ambiguous, stop and ask. Never edit `/contracts/` or `/conventions/` unless the user asks; the index below shows who is affected.
- **Code sharing** only between projects of the same module. Each module defines its own DTOs for shared contracts (tolerant reader: ignore unknown JSON fields).
- **Build per module:** `dotnet build` on the module `.slnx`; in `portal` and `customer` also `npm ci` and `npx ng build`; in `infra` `az bicep build`.
- **No automated tests** unless the user asks. **No Docker** needed locally.
- **Commit per module**, message prefixed with the module folder (`platform: …`).

## Secrets, keys and Azure credentials

- **Never put a secret in a tracked file**: no keys, passwords, SAS tokens, connection strings containing keys, JWT signing keys, certificates or private keys in code, config, docs, scripts, examples or commit messages.
- **Azure access uses identities, not keys.** In Azure: managed identities (`AZURE_CLIENT_ID`). Locally: the developer's `az login` session through `DefaultAzureCredential`. Do not create service principals, client secrets or storage/Service Bus keys for development.
- **Runtime secrets live in Key Vault** (created by `infra`). Local runs read them from git-ignored files generated by `infra/scripts/local-env.sh`: `.env.local` in `portal/` and `customer/`, `.env.<app>.local` in `platform/`.
- **Every runnable project commits an example file** (`.env.example`, or `.env.<app>.example` in `platform/`) listing every variable from its `contracts/environment/` file with empty values or obvious placeholders — never real values.
- **The root `.gitignore` excludes secret files** (`.env*` except examples, `*.pfx`, `*.pem`, `*.key`, `secrets/`, `infra/.state/`). Do not weaken it. If you introduce a new kind of secret file, add its pattern to `.gitignore` in the same change.
- **Before committing**, check `git status` for anything secret; never use `git add -f` on ignored files.
- **Scripts and logs never print secret values.** Print the command that fetches a secret instead (`az keyvault secret show …`).

## .NET conventions (edge, platform, portal, customer)

- .NET 10 (LTS), C# latest, nullable enabled, `TreatWarningsAsErrors` true, implicit usings on.
- ASP.NET Core minimal APIs for HTTP services; `BackgroundService` for workers.
- One solution file `{Module}.slnx` at the module root; projects under `src/` unless the module file says otherwise.
- Configuration only from environment variables (`contracts/environment/`); fail fast at startup when a required one is missing. No secrets in `appsettings*.json`.
- Azure auth: `ManagedIdentityCredential` with `AZURE_CLIENT_ID` in Azure; `DefaultAzureCredential` locally.
- Data access: `Microsoft.Data.SqlClient` + Dapper unless the module says otherwise. Parameterised SQL only.
- JSON: `System.Text.Json`, camelCase, enums as strings, ISO-8601 UTC timestamps ending in `Z`, lowercase GUIDs.
- Errors: RFC 9457 `application/problem+json`, `type` = the error code named in the contract.
- Observability: OpenTelemetry with the Azure Monitor exporter. Log scopes carry `tenantId`, `siteId`, `collectorId`, `correlationId` where known.
- Health: `/healthz` (liveness, no dependencies) and `/readyz` (dependencies reachable).
- Containers: multi-stage Dockerfiles, SDK image to build, `mcr.microsoft.com/dotnet/aspnet:10.0` (or `runtime:10.0` for workers) to run, non-root user, port 8080.

**Naming:** Azure prefix `{prefix}` (default `modpoc`) plus a short unique suffix. Resource groups `rg-{prefix}-prod` (production space) and `rg-{prefix}-ctrl` (controller space).

## PoC labelling rule

Anything that exists only for the demonstration — the simulator UI and API, the simulator Service Bus channel, the processing delay knob, collector provisioning by the simulator — must be labelled **demo scaffolding** wherever it is visible: UI banners, response header `X-Mod-Demo-Scaffolding: true`, a header comment in each file, and the module README.
